# Prompt for Codex: Expense Sheet Email Deep Link Resolver in IND_CRM_APP

Use this prompt in project `C:\INDProjects\IND_CRM_APP`.

Date: 2026-05-25

## Goal

Implement the CRM web deep-link resolver used by expense sheet notification emails.

The web app must support links generated by Axapta and `IND_CRM_API`:

```text
/Gastos/ExpenseSheetLink?hojaGastosId={id}&targetCompanyId={companyId}&source={source}
```

The resolver must:

1. Preserve the link through login.
2. Validate that the authenticated user can access the target company and expense sheet.
3. Switch the current company context if needed using existing web app mechanisms.
4. Redirect to the existing expense sheet detail page:

```text
/Gastos/ExpenseSheetDetail?hojaGastosId={id}
```

It must never approve, reject, pay, or mutate the expense sheet.

## Route contract

Add an explicit route before the default route if route order matters:

```text
GET /Gastos/ExpenseSheetLink
```

Query params:

```text
hojaGastosId      required
targetCompanyId  required
source           optional
```

Examples:

```text
/Gastos/ExpenseSheetLink?hojaGastosId=12345&targetCompanyId=es01&source=axapta
/Gastos/ExpenseSheetLink?hojaGastosId=12345&targetCompanyId=es01&source=crm-api
```

Do not trust `source` for authorization decisions. It is only trace/debug metadata.

## Suggested controller

Add:

```text
Web/Controllers/Gastos/ExpenseSheetLinkController.cs
```

Suggested action:

```csharp
[HttpGet]
public async Task<IActionResult> Index(string hojaGastosId, string targetCompanyId, string source)
```

Behavior:

1. Validate required query params.
2. If the user is not authenticated, redirect to login and preserve the full original URL as `returnUrl`.
3. After authentication, continue resolving the original link.
4. Validate the user can access `targetCompanyId` with the existing company/session logic.
5. Switch active company to `targetCompanyId` if it is not already active.
6. Validate the user can access the specific expense sheet by calling the existing expense sheet detail API or service.
7. Redirect to:

```text
/Gastos/ExpenseSheetDetail?hojaGastosId={id}
```

8. If validation fails, redirect to the existing gastos list or safe home route with a localized message.

Never redirect directly to a raw `returnUrl` unless it is local and validated. Use the app's existing local URL validation helper if one exists.

## Login returnUrl preservation

Update login flow only if needed:

- `AuthController` must accept and preserve `returnUrl`.
- `Login.cshtml` must include hidden `returnUrl` in the login form if the existing flow does not already do this.
- After successful login, redirect to the local `returnUrl`.
- If `returnUrl` is missing or unsafe, redirect to the normal post-login route.

Preserve the complete deep-link query string:

```text
/Gastos/ExpenseSheetLink?hojaGastosId=12345&targetCompanyId=es01&source=axapta
```

## Authorization and middleware

Check whether `INDModuleAuthorizeFilter` or `TokenRefreshMiddleware` blocks the resolver before company context has been resolved.

Required behavior:

- Unauthenticated users can be redirected to login with the original deep link preserved.
- Authenticated users without company access see a localized error and are not redirected to detail.
- Authenticated users without expense sheet access see a localized error and are not redirected to detail.
- Token refresh must not drop the original resolver query string.

If the existing module authorization requires a menu/module permission for gastos, apply the same permission expected for opening expense sheet detail. Do not create a weaker bypass.

## API usage

Use the existing expense sheet detail API call already used by the detail page when possible.

Validation should ensure:

- The sheet exists.
- It belongs to `targetCompanyId`.
- The current user can access it.

Do not duplicate server authorization rules in client code if the API already enforces them.

## Security requirements

- Treat all query params as untrusted.
- Validate `returnUrl` is local before redirecting.
- Do not allow open redirects.
- Do not expose company IDs or sheet IDs in error details beyond normal app behavior.
- Do not mutate expense sheet state from this resolver.
- Do not accept action tokens in this route.

## Verification

Run the established build/test workflow for `IND_CRM_APP`.

Manual verification checklist:

- Opening resolver while logged out redirects to login and then returns to the same resolver URL.
- Opening resolver while logged in and already in the target company redirects to detail.
- Opening resolver while logged in and in another allowed company switches context and redirects to detail.
- Opening resolver with missing `hojaGastosId` shows localized failure and redirects safely.
- Opening resolver with missing `targetCompanyId` shows localized failure and redirects safely.
- Opening resolver for a company the user cannot access is denied.
- Opening resolver for a sheet the user cannot access is denied.
- Final detail URL is `/Gastos/ExpenseSheetDetail?hojaGastosId={id}`.
- No approval, rejection, payment, or update happens from the resolver.
