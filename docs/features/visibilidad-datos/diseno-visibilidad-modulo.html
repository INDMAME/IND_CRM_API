Diseño funcional y técnico - Visibilidad por módulo

Fuente: Propuesta funcional y Propuesta técnica. Exportado: 2026-06-04. Actualizado localmente: 2026-06-09.

Resumen: la solución añade una capa de visibilidad a nivel registro sobre el permiso web actual de Axapta. Mantiene la autorización por empresa, aplicación y módulo, y añade reglas para decidir si un usuario ve solo sus registros, su jerarquía, targets manuales o todos los registros permitidos.
Estado 2026-06-09: el piloto activo es CRM / VISITAS_GESTION. Hojas de gastos conserva su lógica legacy de subordinados basada en CRMUsuarioSubordinadoTable; no se migra ni se reemplaza en esta fase. La API CRM expone GET /api/crm/data-visibility/visible-users y el listado de visitas acepta ownerAxUserId para filtrar dentro de los usuarios visibles. La lista de usuarios visibles solo devuelve personas que tengan INDPersonaTable.UserId resoluble.

1. Diseño funcional

Resumen ejecutivo

Esta propuesta define una capa simple de visibilidad de datos sobre la configuración actual de permisos web de Axapta.

La base actual se mantiene:

INDCiasPermitidas
-> INDWebModuleAccessLevel
-> INDWebModule
-> INDWebApp

El cambio principal es añadir una capa de visibilidad por registros que se pueda configurar de forma funcional, sin reutilizar CRMUsuarioSubordinadoTable.

La versión simplificada queda así:

Permiso web actual por empresa, aplicación y módulo
+ modo base de visibilidad en INDWebModuleAccessLevel
+ jerarquía base por empresa
+ targets manuales para agregar o quitar personas por módulo

La jerarquía no se define por ModuleCode ni por AppCode. Se define solo por empresa, mediante CompanyId. Después, cada módulo ajusta esa jerarquía con INDModuleDataVisibilityTarget, agregando o quitando personas concretas desde la fila de permiso web del módulo.

Los campos de persona de las nuevas tablas se relacionan directamente con INDPersonaTable.Alias.

Convención de nombres

  • Los objetos nuevos de Axapta llevan prefijo IND.
  • Los campos internos no necesitan ese prefijo.
  • Ejemplo: el campo funcional DataVisibilityMode usa el enum técnico INDDataVisibilityMode.
  • Ejemplo: el campo funcional HierarchyDepth usa el enum técnico INDDataVisibilityHierarchyDepth.
  • Ejemplo: el campo funcional TargetScope usa el enum técnico INDDataVisibilityTargetScope.

Nuevo control de profundidad de jerarquía

Se añade el campo HierarchyDepth para decidir hasta dónde baja la jerarquía cuando el modo de visibilidad usa subordinados.

  • DirectOnly / Solo directos: solo incluye subordinados directos del usuario o del target configurado.
  • FullDescendants / Jerarquía completa: incluye todos los descendientes hacia abajo, sin límite funcional de niveles.

Este campo aplica cuando DataVisibilityMode usa jerarquía, por ejemplo OwnAndHierarchy o HierarchyOnly, y también cuando un target manual tiene TargetScope = TargetAndHierarchy.

Valor por defecto recomendado: FullDescendants, para mantener el comportamiento planteado originalmente en la propuesta.

Objetivo funcional

Permitir que una persona pueda ver:

  • Solo sus registros.
  • Sus registros y la jerarquía de personas configurada para la empresa, pudiendo limitarla a subordinados directos o permitir jerarquía completa.
  • Solo la jerarquía de la empresa, pudiendo limitarla a subordinados directos o permitir jerarquía completa.
  • Solo personas agregadas manualmente para un módulo.
  • Todos los registros permitidos por empresa y módulo.

Además, permitir ajustes manuales por módulo:

  • Agregar una persona concreta.
  • Agregar una persona y su jerarquía según la profundidad configurada.
  • Quitar una persona concreta.
  • Quitar una persona y su jerarquía según la profundidad configurada.
Regla clave: si una persona aparece por varias vías de visibilidad, pero existe al menos una configuración vigente que la marque como Quitar, esa persona queda fuera del resultado visible.

Regla clave: quitar siempre prevalece

Esta regla debe quedar como principio funcional y técnico de la solución.

Jerarquía base agrega a PGARCIA
Target manual agrega a PGARCIA
Target manual quita a PGARCIA
Resultado final: PGARCIA no visible

La regla aplica también cuando se quita una jerarquía completa. Si una persona pertenece a una rama quitada, queda descartada aunque otra línea la agregue por jerarquía o por target manual.

Base actual que se conserva

  • INDWebUserEntraIdentity sigue vinculando Entra con el usuario Axapta.
  • INDCiasPermitidas sigue indicando a qué empresas tiene acceso el usuario.
  • INDWebModuleAccessLevel sigue indicando a qué módulos tiene acceso el usuario y con qué AccessRights.
  • INDWebModule e INDWebApp siguen siendo el catálogo de módulos y aplicaciones.
  • El frontend seguirá usando los permisos para mostrar u ocultar acciones.
  • La API y Axapta seguirán haciendo la validación real de seguridad.

Cambio funcional importante

  • La jerarquía base se define solo por CompanyId.
  • Esa misma jerarquía puede servir para todas las aplicaciones y módulos de la empresa.
  • Las diferencias por módulo se gestionan desde INDModuleDataVisibilityTarget.
  • INDModuleDataVisibilityTarget puede agregar o quitar personas para un permiso de módulo concreto.
Empresa: AZM
Jerarquía base:
MMEZA -> JLOPEZ -> PGARCIA

Para VISITAS_GESTION, se usa la nueva jerarquía como piloto. GASTOS_HOJA_GASTO queda como módulo legacy en fase 1: mantiene su lógica actual de subordinados y no debe mezclarse con INDControlDataVisibility hasta una migración posterior.

Cómo se configura en Axapta

En la pantalla actual de Accesos Web, dentro de los módulos web, se añadirían columnas resumen.

Código sitio web ModuleCode AccessRights Visibilidad Profundidad Mutaciones Targets
CRM VISITAS_GESTION Control total Propios + jerarquía Completa Propios 2 agregados
CRM GASTOS_HOJA_GASTO Legacy Subordinados actuales No aplica fase 1 Reglas legacy No migrado
CRM GASTOS_TICKETS Edición Solo propios No aplica Reglas del módulo 0

Botones recomendados:

  • Jerarquía: configura la jerarquía base de la empresa.
  • Targets: configura reglas manuales de agregar/quitar para el módulo seleccionado.

Ejemplo funcional 1: agregar persona puntual

Usuario: MMEZA
Empresa: AZM
AppCode: CRM
Módulo: VISITAS_GESTION
DataVisibilityMode: OwnAndHierarchy
Target: JLOPEZ
TargetAction: Add / Agregar
TargetScope: TargetOnly / Solo persona
  • MMEZA ve sus propios registros.
  • MMEZA ve su jerarquía base de la empresa AZM.
  • MMEZA también ve los registros de JLOPEZ en el módulo configurado.
  • No ve la jerarquía de JLOPEZ por esta regla puntual.

Ejemplo funcional 2: agregar persona con jerarquía

Target: JLOPEZ
TargetAction: Add / Agregar
TargetScope: TargetAndHierarchy / Persona + jerarquía
HierarchyDepth: FullDescendants / Jerarquía completa
  • Se agrega JLOPEZ.
  • También se agregan todos los descendientes de JLOPEZ dentro de la misma empresa porque HierarchyDepth = FullDescendants.
  • Si HierarchyDepth = DirectOnly, solo se agregarían sus subordinados directos.

Ejemplo funcional 3: ver solo subordinados directos

DataVisibilityMode: OwnAndHierarchy
HierarchyDepth: DirectOnly / Solo directos

Jerarquía:

Director
  -> Jefe A
      -> Usuario 1
      -> Usuario 2
  • El Director ve sus propios registros.
  • El Director ve los registros de Jefe A.
  • El Director no ve los registros de Usuario 1 ni Usuario 2, porque son subordinados del subordinado.
  • Esta configuración sirve cuando se quiere permitir control directo sin heredar equipos completos de otros jefes.

Ejemplo funcional 4: quitar persona puntual

DataVisibilityMode: OwnAndHierarchy
Target: PGARCIA
TargetAction: Remove / Quitar
TargetScope: TargetOnly / Solo persona
  • Primero se resuelve la visibilidad base.
  • Después se quita PGARCIA del resultado visible para el módulo configurado.
  • No se quitan sus descendientes.

Ejemplo funcional 5: quitar persona y su jerarquía

Target: JLOPEZ
TargetAction: Remove / Quitar
TargetScope: TargetAndHierarchy / Persona + jerarquía
HierarchyDepth: FullDescendants / Jerarquía completa
  • Se quita JLOPEZ del resultado visible del módulo configurado.
  • También se quitan todos los descendientes de JLOPEZ dentro de la misma empresa porque HierarchyDepth = FullDescendants.
  • Si HierarchyDepth = DirectOnly, solo se quitarían sus subordinados directos.
  • Esta regla permite recortar una rama completa o solo el primer nivel sin modificar la jerarquía base.

Herencia, duplicados y prioridad

La jerarquía soporta dos formas de profundidad configurables por módulo:

  • DirectOnly / Solo directos: recorre únicamente el primer nivel de subordinados.
  • FullDescendants / Jerarquía completa: recorre todos los niveles descendentes hasta que no haya más personas.
Director
  -> Jefe A
      -> Usuario X
  -> Jefe B
      -> Usuario X

Resultado efectivo:

Jefe A, Jefe B, Usuario X
  • Con FullDescendants, la jerarquía se recorre hasta que no haya más descendientes.
  • Con DirectOnly, solo se toma el primer nivel de subordinados.
  • Si una persona aparece por varias ramas, aparece una sola vez.
  • Si hay ciclos, el resolver corta la rama usando un conjunto de personas ya visitadas.
  • Remove / Quitar tiene prioridad sobre Add / Agregar, sobre la jerarquía base, sobre HierarchyDepth y sobre AllUsers.
  • Las reglas solo se consideran vigentes si sus fechas ValidFrom y ValidTo aplican al día de consulta.
  • No se permite configurar al propio usuario visor como target manual; para excluir propios se debe usar un modo base que no incluya propios.

Decisiones funcionales cerradas

  • La propuesta válida para análisis es la versión simplificada.
  • La jerarquía base se define por empresa, no por aplicación ni por módulo.
  • Las diferencias por módulo se resuelven con targets manuales.
  • Los targets manuales pueden agregar o quitar.
  • En jerarquías y targets, Active será un dato informativo calculado por ValidFrom y ValidTo; no se mantiene un IsActive físico.
  • Se añade HierarchyDepth, basado en el enum técnico INDDataVisibilityHierarchyDepth, para definir si la jerarquía baja solo a subordinados directos o a todos los descendientes.
  • El antiguo check IncludeTargetHierarchy se sustituye por el campo TargetScope, basado en el enum técnico INDDataVisibilityTargetScope.
  • Los campos de persona usan INDPersonaTable.Alias.
  • INDPersonaTable.Alias se considera único para esta solución.
  • Las personas con INDPersonaTable.Blocked = Sí quedan excluidas siempre de la visibilidad y de la configuración vigente.

Decisiones confirmadas y aclaraciones antes de implementar

  • INDPersonaTable.Alias es único y será la identidad funcional de visibilidad.
  • Las relaciones de jerarquía y targets se validan siempre contra INDPersonaTable.Alias.
  • Solo se consideran personas con INDPersonaTable.Blocked = No; una persona bloqueada no debe aparecer como visible ni poder guardarse como configuración vigente.
  • No se permite que una persona sea su propio subordinado: ParentPersonAlias debe ser distinto de ChildPersonAlias.
  • No se permite configurar al usuario visor como su propio target manual; su propia visibilidad se controla con DataVisibilityMode.
  • La profundidad de subordinados se controla con HierarchyDepth: DirectOnly para primer nivel o FullDescendants para toda la rama.
  • "Propietario real del registro" no significa el jefe que accede al módulo. Es el campo de cada tabla de negocio que identifica de quién es el registro y que debe poder mapearse a INDPersonaTable.Alias.
  • En el módulo piloto de visitas, el propietario funcional implementado es CRMActividadTable.INDCreatedByUserId, con compatibilidad legacy para resolver CRMActividadTable.UserId cuando sea necesario.

2. Diseño técnico

Objetivo técnico

Esta sección contiene el detalle técnico de la capa simple de visibilidad por módulo.

Convención de nombres AX

Los objetos nuevos de Axapta deben llevar prefijo IND para identificarlos como objetos Insertec: enums, tablas, formularios, clases, EDTs si se crean, menús y elementos de menú.

Los campos internos de una tabla nueva o existente no necesitan el prefijo IND. Por ejemplo, el campo puede llamarse DataVisibilityMode, pero el enum AX que usa debe llamarse INDDataVisibilityMode. El campo HierarchyDepth debe usar el enum AX INDDataVisibilityHierarchyDepth.

1. Campos nuevos en tabla existente

Tabla existente: INDWebModuleAccessLevel

Esta tabla sigue siendo la base del permiso web por usuario, empresa, aplicación y módulo. La propuesta simple añade aquí el modo base de visibilidad y la política de mutaciones.

Campo nuevo Tipo conceptual Obligatorio Valor por defecto Descripción
DataVisibilityMode INDDataVisibilityMode Sí OwnOnly Define el conjunto base de personas visibles para el módulo.
HierarchyDepth INDDataVisibilityHierarchyDepth Sí FullDescendants Define si la jerarquía baja solo al primer nivel o a todos los descendientes. Solo aplica cuando se usa jerarquía.
MutationPolicy INDMutationPolicy Sí ModuleBusinessRules Define cómo tratar edición y eliminación sobre registros visibles.

2. Enum AX nuevo: INDDataVisibilityMode

El modo define el conjunto base. Después se aplican los targets manuales.

Valor Significado Incluye persona actual Incluye jerarquía base Usa targets
OwnOnly Solo registros propios. Sí No Sí, como ajuste posterior.
OwnAndHierarchy Propios + jerarquía base de la empresa. Sí Sí Sí, como ajuste posterior.
HierarchyOnly Solo jerarquía base, sin propios. No Sí Sí, como ajuste posterior.
ManualTargetsOnly Solo personas agregadas manualmente. No No Sí.
AllUsers Todos los registros de la empresa/módulo. N/A N/A Sí, principalmente para quitar excepciones.

3. Enum AX nuevo: INDDataVisibilityHierarchyDepth

Este enum define hasta dónde se recorre la jerarquía cuando el modo base o un target manual incluye jerarquía.

Valor Significado Uso recomendado
DirectOnly Incluye únicamente subordinados directos del usuario visor o del target configurado. Cuando un jefe debe ver solo su equipo directo, sin heredar equipos de jefes subordinados.
FullDescendants Incluye todos los descendientes hacia abajo, sin límite funcional de niveles. Cuando un jefe superior debe ver jefaturas completas y sus equipos.

Valor por defecto recomendado: FullDescendants, para conservar el comportamiento inicial de jerarquía completa.

4. Enum AX nuevo: INDMutationPolicy

Valor Descripción Uso recomendado
OwnOnly Solo permite editar/eliminar registros propios. Lectura amplia, escritura conservadora.
SameAsVisibility Permite editar/eliminar todo lo visible. Solo si negocio lo aprueba.
ModuleBusinessRules El módulo aplica sus reglas específicas. Módulos legacy o reglas específicas posteriores. Hojas de gastos no se migra en fase 1.

5. Enum AX nuevo: INDDataVisibilityTargetAction

Este enum se usa en INDModuleDataVisibilityTarget para indicar si una persona configurada se agrega o se quita.

Valor técnico Etiqueta visual Descripción
Add Agregar Agrega la persona indicada al resultado visible del módulo.
Remove Quitar Quita la persona indicada del resultado visible del módulo. Siempre prevalece.

Valor por defecto recomendado: Add.

6. Enum AX nuevo: INDDataVisibilityTargetScope

Este enum sustituye el antiguo check IncludeTargetHierarchy. La idea es que la UI no muestre un check ambiguo, sino un alcance claro.

Valor técnico Etiqueta visual Descripción
TargetOnly Solo persona La acción aplica solo sobre TargetPersonAlias.
TargetAndHierarchy Persona + jerarquía La acción aplica sobre TargetPersonAlias y su jerarquía usando la profundidad configurada en HierarchyDepth.

7. Tabla nueva: INDModuleDataVisibilityHierarchyLine

Sirve para configurar la jerarquía base por empresa. Ya no depende de ModuleCode ni de AppCode. Los campos de persona se relacionan con INDPersonaTable.Alias.

Campo Tipo conceptual Obligatorio Descripción
RecId int64 Sí Identificador interno del registro.
CompanyId DataAreaId/string Sí Empresa donde aplica la relación. Debe corresponder con INDCiasPermitidas.CiaId.
ParentPersonAlias string / EDT Alias Sí Alias de INDPersonaTable que actúa como responsable o superior.
ChildPersonAlias string / EDT Alias Sí Alias de INDPersonaTable que queda debajo del responsable.
Active display NoYes No persistente Campo informativo calculado con ValidFrom y ValidTo respecto al día actual.
ValidFrom date No Fecha desde la que aplica la relación.
ValidTo date No Fecha hasta la que aplica la relación.
ReasonText string/text No Motivo funcional de la relación.

Relaciones recomendadas

Campo Relación Comentario
CompanyId INDCiasPermitidas.CiaId / empresa de trabajo Debe validar empresa existente.
ParentPersonAlias INDPersonaTable.Alias Lookup de persona superior.
ChildPersonAlias INDPersonaTable.Alias Lookup de persona descendente.

Índices recomendados

Índice Campos Duplicados Uso
HierarchyUniqueIdx CompanyId + ParentPersonAlias + ChildPersonAlias + ValidFrom + ValidTo No duplicados exactos Evitar relaciones duplicadas para la misma vigencia.
HierarchyParentIdx CompanyId + ParentPersonAlias + ValidFrom + ValidTo Sí Resolver descendientes vigentes.
HierarchyChildIdx CompanyId + ChildPersonAlias + ValidFrom + ValidTo Sí Validar dependencias, vigencias y ciclos.

Validaciones obligatorias

  • No permitir ParentPersonAlias = ChildPersonAlias.
  • Validar que ambos alias existan en INDPersonaTable.
  • Validar que ambos alias tengan INDPersonaTable.Blocked = No.
  • Validar vigencias si se usan ValidFrom y ValidTo.
  • Avisar o bloquear ciclos al guardar, aunque el resolver también debe protegerse.

8. Tabla nueva: INDModuleDataVisibilityTarget

Sirve para modificar la visibilidad efectiva de un permiso de módulo concreto. Puede agregar o quitar personas. Los campos de persona se relacionan con INDPersonaTable.Alias.

Campo Tipo conceptual Obligatorio Descripción
RecId int64 Sí Identificador interno del registro.
ModuleAccessLevelRecId int64 Sí Relación con la fila de permiso web del módulo.
TargetPersonAlias string / EDT Alias Sí Alias de INDPersonaTable que se agrega o se quita.
TargetAction INDDataVisibilityTargetAction Sí Indica si el target se agrega o se quita.
TargetScope INDDataVisibilityTargetScope Sí Indica si la acción aplica solo a la persona o también a su jerarquía.
Active display NoYes No persistente Campo informativo calculado con ValidFrom y ValidTo respecto al día actual.
ValidFrom date No Fecha desde la que aplica la regla.
ValidTo date No Fecha hasta la que aplica la regla.
ReasonText string/text No Motivo funcional de agregar o quitar.

Relaciones recomendadas

Campo Relación Comentario
ModuleAccessLevelRecId INDWebModuleAccessLevel.RecId Permite aplicar la regla a un usuario, empresa, aplicación y módulo concretos.
TargetPersonAlias INDPersonaTable.Alias Lookup de persona agregada o quitada. Solo personas con Blocked = No.

Validaciones obligatorias

  • Validar que TargetPersonAlias exista en INDPersonaTable.
  • Validar que TargetPersonAlias tenga INDPersonaTable.Blocked = No.
  • No permitir que TargetPersonAlias sea el alias del usuario visor asociado a ModuleAccessLevelRecId.
  • Validar ValidFrom <= ValidTo si ambas fechas existen.
  • No mantener IsActive físico; Active será un display calculado por vigencia.
  • Mantener TargetAction = Remove / Quitar como regla de mayor prioridad.

Índices recomendados

Índice Campos Duplicados Uso

TargetActionIdx ModuleAccessLevelRecId + TargetAction + ValidFrom + ValidTo Sí Separar agregados y quitados vigentes.

9. Resolución de visibilidad

Para el MVP puede resolverse con métodos estáticos de tabla y INDCRMUtilityService. Si se crea una clase específica para centralizar el algoritmo, el nombre recomendado del objeto AX es INDControlDataVisibilityResolver.

Paso Acción
1 Validar empresa, usuario y AccessRights del módulo.
2 Resolver el alias funcional del usuario visor desde INDPersonaTable.
3 Construir el conjunto base según el campo DataVisibilityMode.
4 Resolver jerarquía base con CompanyId y HierarchyDepth cuando aplique.
5 Aplicar targets Add / Agregar vigentes del permiso de módulo. Si el target usa TargetAndHierarchy, aplicar HierarchyDepth.
6 Aplicar targets Remove / Quitar vigentes del permiso de módulo. Si el target usa TargetAndHierarchy, aplicar HierarchyDepth.
7 Eliminar duplicados y devolver un conjunto único de alias visibles.
8 Filtrar listados y detalles por propietario del registro.

Regla de prioridad: Remove / Quitar gana sobre cualquier regla de Add / Agregar, sobre jerarquía, sobre HierarchyDepth y sobre AllUsers. Si una persona aparece en varios bloques, una sola línea vigente de quitar basta para descartarla.

10. Propietario del registro

Para que el filtro sea consistente, cada módulo debe poder resolver el propietario del registro a INDPersonaTable.Alias.

El propietario real del registro no es el jefe que consulta ni el usuario que abre la pantalla. Es el dato del registro de negocio que indica a qué persona pertenece el registro visible: creador, responsable, comercial, empleado, usuario asignado o equivalente según el módulo.

La integración debe mapear ese valor a INDPersonaTable.Alias antes de aplicar el filtro.

Módulo Campo propietario recomendado Estado
Módulos nuevos Alias de INDPersonaTable directo o mapeable. Recomendado.
Visitas CRMActividadTable.INDCreatedByUserId, mapeado a INDPersonaTable.UserId y INDPersonaTable.Alias. Implementado para piloto VISITAS_GESTION.
Hojas de gastos CRMHojaGastosTable.UserId como CRMUserId. Legacy; no migrar en fase 1.
Tickets Pendiente de confirmar. No migrar sin análisis.

11. Denegación por defecto

Situación Comportamiento
No hay DataVisibilityMode Aplicar OwnOnly.
No se puede resolver alias del usuario visor No conceder visibilidad ampliada.
No se puede resolver propietario del registro No conceder visibilidad ampliada.
Persona inexistente o bloqueada Excluir siempre del resultado visible y no permitir como configuración vigente.
Configuración circular Cortar rama al detectar alias ya visitado.
Módulo legacy no migrado Mantener comportamiento actual.

12. Impacto en PermissionsRevision

Debe cambiar PermissionsRevision cuando cambie cualquiera de estos elementos:

  • AccessRights.
  • DataVisibilityMode.
  • HierarchyDepth.
  • MutationPolicy.
  • INDModuleDataVisibilityHierarchyLine.
  • INDModuleDataVisibilityTarget.
  • Vigencias de jerarquías y targets.

13. Tablas que no se reutilizan

Tabla Motivo
CRMUsuarioSubordinadoTable Usa CRMUserId, no INDPersonaTable.Alias; no separa por empresa y no tiene vigencia ni estado activo.
CRMUsuarioTable Puede servir para mapeos legacy, pero no debe ser la identidad principal de la nueva jerarquía.
