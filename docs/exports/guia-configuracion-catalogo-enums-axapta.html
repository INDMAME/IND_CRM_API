Guía funcional - Configuración de catálogo de enums en Axapta

Fuente: .codex/Axapta/INDAxEnumAppCatalogTable.xpo y .codex/Axapta/INDAxEnumAppCatalogTableForm.xpo. Exportado: 2026-06-19.

Objetivo: explicar cómo configurar en Axapta qué valores de un enum AX quedan disponibles para un aplicativo, por company, con etiqueta, descripción, orden y opción de copia entre empresas.

Alcance

Esta guía describe la parametrización funcional del formulario INDAxEnumAppCatalogTableForm. No explica cómo crear enums nuevos en AX ni cómo consumirlos desde la API; el foco es cargar y mantener el catálogo público que después leerán los servicios.

La configuración se apoya en la tabla técnica INDAxEnumsTable, que contiene los valores reales del enum AX, y en la tabla INDAxEnumAppCatalogTable, que decide qué opciones se exponen para cada aplicativo y company.

Objetos AX

INDAxEnumsTable

Tabla técnica con el inventario de valores de enums AX. Aporta AxEnumName, AxEnumId, EnumIndex, EnumValue, Description y RecId.

  • EnumValue es el valor numérico real que debe viajar hacia la aplicación.
  • Description funciona como texto base cuando no hay etiqueta personalizada.
  • RecId se usa como referencia técnica desde el catálogo público.

INDAxEnumAppCatalogTable

Tabla funcional de configuración. Tiene SaveDataPerCompany = Yes, por lo que la company se controla con el DataAreaId estándar de Axapta.

  • No existe campo funcional Company.
  • No existe campo Visible; la exposición se controla con Active.
  • El índice único AppEnumRefIdx evita duplicados por AppCode + AxEnumsTableRefRecId dentro de la company actual.

INDAxEnumAppCatalogTableForm

Formulario de mantenimiento. Muestra los enums disponibles, sus valores técnicos y la configuración pública asociada al valor seleccionado.

  • Datasource superior izquierdo: INDAxEnumsTableGrouped.
  • Datasource superior derecho: INDAxEnumsTable.
  • Datasource inferior: INDAxEnumAppCatalogTable.
  • Botón funcional: Copiar configuración.

Distribución del formulario

La pantalla está organizada en tres zonas principales.

  1. Enumerados agrupados: lista los enums por AxEnumName y AxEnumId. Sirve para elegir el enum funcional que se va a parametrizar.
  2. Valores del enumerado: muestra las opciones del enum seleccionado, con Description, EnumIndex, AxEnumId y EnumValue.
  3. Catálogo público: permite crear las filas que expondrá el aplicativo para el valor técnico seleccionado.

Al cambiar el enum agrupado, el datasource INDAxEnumsTableGrouped ejecuta INDAxEnumsTable_ds.executeQuery() para refrescar la lista de valores del enum. El datasource inferior queda enlazado al valor seleccionado de INDAxEnumsTable.

Regla de configuración

La regla principal es simple: se crea un registro en INDAxEnumAppCatalogTable por cada valor de enum que se quiera exponer.

Ejemplo: si el enum ABC tiene cuatro valores técnicos, pero la aplicación CRM solo debe mostrar Ninguno y B, se crean dos filas activas en el catálogo público: una para Ninguno y otra para B.

Los valores que no tengan fila activa no se devuelven a la aplicación. Marcar una fila como Active = No también la retira del catálogo público sin borrar el histórico.

Campos configurables

AppCode

Identifica el aplicativo consumidor. Para CRM se usa CRM. Está relacionado con INDWebApp.AppCode.

SortOrder

Define el orden de presentación en la aplicación. La validación impide que dos valores activos del mismo enum y aplicativo compartan el mismo orden.

0 es un orden válido. Los índices parten desde 0 y aumentan progresivamente.

LabelOverride

Etiqueta visible para el usuario final. Si está vacía, se usa INDAxEnumsTable.Description.

DescriptionOverride

Descripción funcional opcional. Si está vacía, se usa INDAxEnumsTable.Description.

Active

Indica si el valor está disponible para el aplicativo en la company actual. Sustituye al concepto de Visible.

Alta de una opción

  1. Entrar en la company donde se quiere configurar el catálogo.
  2. Abrir el formulario Catálogo de enums por aplicativo.
  3. Seleccionar el enum en la lista agrupada de Enumerados.
  4. Seleccionar el valor técnico concreto en la grilla de valores.
  5. Crear una nueva fila en Catálogo público.
  6. Informar AppCode, normalmente CRM.
  7. Informar SortOrder con un orden único para ese enum y aplicativo.
  8. Opcionalmente informar LabelOverride y DescriptionOverride.
  9. Dejar Active = Yes si la opción debe exponerse.

Validaciones

La tabla INDAxEnumAppCatalogTable concentra las validaciones para que apliquen tanto desde el formulario como desde procesos de copia o carga.

  • AppCode es obligatorio.
  • AxEnumsTableRefRecId es obligatorio y debe existir en INDAxEnumsTable.
  • No puede existir más de una configuración activa para el mismo AppCode + AxEnumsTableRefRecId en la company actual.
  • No puede repetirse el mismo SortOrder para dos valores activos distintos del mismo AxEnumName + AxEnumId y AppCode.

La validación de orden se implementa con checkSortOrderUnique() y se invoca desde validateField() y validateWrite().

Copia entre companies

El botón Copiar configuración abre el diálogo Copiar configuracion de enums. Sirve para copiar una configuración completa de una company origen a una company destino.

  • Company origen: company desde la que se leerá la configuración.
  • Company destino: company donde se crearán o actualizarán las filas.
  • AppCode: aplicativo a copiar, por ejemplo CRM.
  • Enum AX: si se deja vacío, copia todos los enums del aplicativo. Si se informa, copia solo ese AxEnumName.
  • Sobrescribir existentes: si está desmarcado, omite registros ya existentes; si está marcado, actualiza orden, etiqueta, descripción y estado.

La copia se ejecuta con copyCompanyAppConfig() usando changecompany(), por lo que respeta el aislamiento por DataAreaId.

Particularidades técnicas

  • El grupo superior usa OrderMode::GroupBy; en AX 3.0 los addSortField() actúan como campos de agrupación.
  • El detalle INDAxEnumsTable filtra por AxEnumName y AxEnumId del grupo seleccionado.
  • Cuando no hay grupo seleccionado, el detalle se bloquea con RecId = 0.
  • Los rangos dinámicos del detalle se mantienen con variables QueryBuildRange para evitar que queden filtros antiguos pegados en la query.
  • El catálogo inferior se enlaza con el valor seleccionado de INDAxEnumsTable mediante la referencia a AxEnumsTableRefRecId.
  • La tabla no duplica AxEnumName, AxEnumId, EnumIndex, EnumValue ni Description; esos datos se leen desde INDAxEnumsTable.

Particularidades funcionales

  • La company no se escribe en un campo visible; depende de la company activa en Axapta.
  • Una opción no configurada no se expone.
  • Una opción configurada con Active = No queda guardada, pero no debería ser devuelta por la API.
  • El valor que debe enviar la aplicación siempre es EnumValue, no EnumIndex.
  • SortOrder solo ordena la presentación; no cambia el valor real del enum.
  • Las etiquetas personalizadas permiten adaptar el texto del frontend sin modificar el enum AX original.

Decisión sobre SortOrder = 0

Decisión cerrada: SortOrder = 0 es válido. El método effectiveSortOrder() debe devolver siempre SortOrder y no hacer fallback a EnumIndex cuando el orden sea 0.

Checklist de carga

  1. Confirmar que se está en la company correcta.
  2. Seleccionar el enum AX correcto en la grilla agrupada.
  3. Crear solo las opciones que debe mostrar el aplicativo.
  4. Comprobar que AppCode coincide con el consumidor real.
  5. Asignar un SortOrder único dentro del mismo enum y aplicativo.
  6. Usar LabelOverride solo si se quiere reemplazar el texto base.
  7. Usar DescriptionOverride solo si se necesita una descripción funcional distinta.
  8. Verificar que Active queda marcado en las opciones que deben salir por API.
  9. Si hay otra company equivalente, usar Copiar configuración en vez de cargar manualmente.

Ejemplo operativo

Para el enum ABC, si se quiere exponer en CRM los valores Ninguno y B, se cargan dos registros activos en Catálogo público, cada uno asociado al valor técnico correspondiente de INDAxEnumsTable.

  • Ninguno: EnumValue = 0, SortOrder = 0 o el orden definido funcionalmente.
  • B: EnumValue = 2, con un SortOrder distinto al de Ninguno.

Si ambos registros están activos y comparten el mismo SortOrder, la validación debe bloquear el guardado.
