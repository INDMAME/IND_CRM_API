Propuesta técnico funcional - Enums por aplicativo

Fuente: página de Notion. Exportado: 2026-06-02.

Diseño funcional

La solución queda cerrada sobre una tabla nueva: INDAxEnumAppCatalogTable. Esta tabla controla qué opciones de los enums de Axapta se exponen para cada aplicativo, usando INDAxEnumsTable como diccionario técnico base.

La configuración queda por aplicativo, por ejemplo CRM. No se enlaza inicialmente con módulo, pantalla o endpoint. La exposición web/API se controla con Active; no existe campo funcional Visible.

Reglas funcionales

  • INDAxEnumsTable contiene todos los valores reales del enum AX.
  • INDAxEnumAppCatalogTable decide qué valores se exponen para cada aplicativo.
  • No hay un identificador funcional adicional entre el aplicativo y el enum.
  • La agrupación de opciones se obtiene siempre desde INDAxEnumsTable, usando AxEnumName o AxEnumId.
  • AxEnumName será la búsqueda principal porque es legible y expresa el objeto AX real.
  • AxEnumId también es un valor válido y se expondrá por un endpoint o método separado.
  • Active = Yes significa que la opción se devuelve para el aplicativo.
  • La API y la web siguen enviando el EnumValue numérico real de AX.
Ejemplo funcional: para el aplicativo CRM y el enum AX CRMGastoType, las opciones habilitadas serán las filas de INDAxEnumsTable enlazadas en INDAxEnumAppCatalogTable.

Diseño técnico

INDAxEnumsTable se mantiene como tabla base del diccionario de AX. Conserva AxEnumName, AxEnumId, EnumIndex, EnumValue, Description y RecId.

INDAxEnumAppCatalogTable tendrá una fila por opción de enum configurada para un aplicativo.

Campos de INDAxEnumAppCatalogTable

  • AppCode: código del aplicativo, por ejemplo CRM.
  • AxEnumsTableRefRecId: referencia directa a INDAxEnumsTable.RecId.
  • SortOrder: orden de presentación. 0 es válido y no significa vacío.
  • LabelOverride: texto opcional; fallback a INDAxEnumsTable.Description.
  • DescriptionOverride: descripción opcional; fallback a INDAxEnumsTable.Description.
  • Active: permite desactivar configuración sin borrar filas.

Relación lógica

  • INDAxEnumAppCatalogTable.AxEnumsTableRefRecId apunta directamente a INDAxEnumsTable.RecId.
  • La tabla nueva no duplica AxEnumName, AxEnumId, EnumValue, EnumIndex ni Description.
  • AxEnumName y AxEnumId se leen siempre desde INDAxEnumsTable.

Flujo de consulta por nombre

  1. Buscar filas en INDAxEnumsTable por AxEnumName.
  2. Tomar los RecId de esas filas.
  3. Buscar en INDAxEnumAppCatalogTable por AppCode, AxEnumsTableRefRecId y Active.
  4. Construir la respuesta leyendo AxEnumName, AxEnumId, EnumValue, EnumIndex y Description desde INDAxEnumsTable.

Flujo de consulta por id

  1. Buscar filas en INDAxEnumsTable por AxEnumId.
  2. Tomar los RecId de esas filas.
  3. Buscar en INDAxEnumAppCatalogTable por AppCode, AxEnumsTableRefRecId y Active.
  4. Construir la misma respuesta que la búsqueda por nombre.

API implementada

Endpoint principal por nombre:

GET /api/crm/enums/by-name?appCode=CRM&axEnumNames=CRMGastoType,INDExpenseSheetStatus

Endpoint separado por id:

GET /api/crm/enums/by-id?appCode=CRM&axEnumIds=123,456

La API debe llamar a INDCRMUtilityService y no hacer joins complejos desde C#. Así el contrato queda estable aunque cambie la implementación interna en AX.

Métodos sugeridos en INDAxEnumAppCatalogTable

  • find(appCode, axEnumsTableRefRecId, forUpdate = false): devuelve la configuración exacta para una opción de enum en un aplicativo.
  • findByAxEnumName(appCode, axEnumName): busca en INDAxEnumsTable por AxEnumName y cruza por AxEnumsTableRefRecId.
  • findByAxEnumId(appCode, axEnumId): busca en INDAxEnumsTable por AxEnumId y cruza por AxEnumsTableRefRecId.
  • effectiveLabel(): usa LabelOverride si existe; si no, usa INDAxEnumsTable.Description.
  • validateWrite(): valida campos obligatorios, existencia de AxEnumsTableRefRecId, duplicados y reglas de estado.

Reglas de validateWrite()

  • AppCode y AxEnumsTableRefRecId son obligatorios.
  • AxEnumsTableRefRecId debe existir en INDAxEnumsTable.
  • No debe existir duplicado activo para AppCode + AxEnumsTableRefRecId.
  • No puede repetirse el mismo SortOrder para dos valores activos distintos del mismo enum y aplicativo.

Métodos sugeridos en INDCRMUtilityService

  • getEnumValuesByName(container _data): método principal de lectura por AxEnumName.
  • getEnumValuesById(container _data): método separado de lectura por AxEnumId.

Entrada sugerida para getEnumValuesByName(container _data)

  1. company
  2. appCode
  3. axEnumNames

Entrada sugerida para getEnumValuesById(container _data)

  1. company
  2. appCode
  3. axEnumIds

Salida sugerida

  • Header estándar: success, message.
  • Una fila por enum solicitado.
  • Items: una fila por opción de enum expuesta.

Recomendaciones de robustez

  • Mantener INDAxEnumsTable estable: no truncar y recrear filas si existen configuraciones apuntando por RecId.
  • Si INDAxEnumsTable puede regenerarse cambiando RecId, definir antes un proceso controlado de relink por AxEnumName + EnumValue.
  • Usar AxEnumName como búsqueda principal.
  • Usar AxEnumId por endpoint/método separado porque también es un valor válido.
  • Crear relación AX desde INDAxEnumAppCatalogTable.AxEnumsTableRefRecId hacia INDAxEnumsTable.RecId.
  • Crear índice único para evitar duplicados activos por AppCode + AxEnumsTableRefRecId.
  • Crear índices de consulta por AppCode + Active y por AxEnumsTableRefRecId.
  • Revisar o crear índice en INDAxEnumsTable por AxEnumName y por AxEnumId.
  • Usar Active = No para retirar configuraciones; evitar borrado físico salvo limpieza controlada.
  • Devolver siempre EnumValue desde INDAxEnumsTable; nunca desde un valor duplicado en la tabla nueva.
  • Validar appCode contra contexto/permiso del usuario cuando el endpoint sea público para frontend.
  • Si se solicita un enum que no existe, devolver error controlado; si existe pero no tiene opciones activas, devolver lista vacía.
  • Mantener compatibilidad: los endpoints existentes siguen recibiendo y devolviendo enteros.

Inventario de enums identificados

Fuente: revisión de los endpoints actuales de CRM/API y de las clases AX exportadas. Los valores exactos deben validarse finalmente contra INDAxEnumsTable, pero este inventario permite empezar a cargar INDAxEnumAppCatalogTable.

Enums AX a configurar en INDAxEnumAppCatalogTable

1. INDExpenseSheetStatus

  • Valores conocidos: 0 Draft, 1 InReview, 2 Approved, 3 Rejected, 4 Paid.
  • Campos API: expenseSheetStatus, ExpenseSheetStatus.
  • Usos: creación, edición, detalle y listado de hojas de gastos; filtros; notificaciones de estado.
  • Prioridad: alta.

2. INDReimbursableExpense

  • Valores conocidos: 0 No, 1 Yes, 2 Both.
  • Campos API: reimbursableExpense, ReimbursableExpense.
  • Usos: cabecera y líneas de hojas de gastos; filtros; propagación de reembolso.
  • Prioridad: alta.

3. INDExchangeRateMode

  • Valores conocidos: pendiente confirmar en INDAxEnumsTable.
  • Campos API: exchangeRateMode, ExchangeRateMode.
  • Usos: cabecera, detalle y listado de hojas de gastos.
  • Observación: la API actual acepta enteros >= 0, pero no tiene la lista completa hardcodeada.
  • Prioridad: media.

4. CRMGastoType

  • Valores conocidos: 0 None, 1 Peaje, 2 Parking, 3 Km, 4 Desayuno, 5 Comida, 6 Cena, 7 Hotel, 8 Varios, 14 Taxi.
  • Campos API: typeValue, gastoType, GastoType.
  • Usos: líneas de hojas de gastos, tickets, filtros de tickets, vinculación masiva, IA de tickets y prompts/schema IA.
  • Prioridad: alta.

5. INDTicketStatus

  • Valores conocidos: 0 Pending, 1 Assigned.
  • Campos API: status, Status.
  • Usos: listado/edición de tickets y estado de vinculación con hojas de gastos.
  • Prioridad: alta.

6. INDContactMethod

  • Valores conocidos: pendiente confirmar en INDAxEnumsTable.
  • Campos API: contactMethod, ContactMethod.
  • Usos: creación y edición de actividades/visitas.
  • Observación: AX usa INDContactMethod::InPerson como valor por defecto cuando no se informa.
  • Prioridad: media.

7. CRMTipoVisita

  • Valores conocidos: pendiente confirmar en INDAxEnumsTable.
  • Campos API: visitType.
  • Usos: creación y edición de actividades/visitas.
  • Observación: ahora viaja como valor numérico en API y AX lo trata como enum CRMTipoVisita.
  • Prioridad: media.

8. CRMCustVendVisitaAsistente

  • Valores conocidos: pendiente confirmar en INDAxEnumsTable.
  • Campos API: asistenteTipo.
  • Usos: creación de asistentes de visita.
  • Observación: ahora viaja como valor numérico en API y AX lo trata como enum CRMCustVendVisitaAsistente.
  • Prioridad: media.

Constantes operativas que no deben ir a INDAxEnumAppCatalogTable

1. Modo de operación de hojas/tickets (mode)

  • Valores: 0 Cabecera+Lineas, 1 Solo cabecera, 2 Agregar lineas a existente.
  • Usos: CreateExpenseSheetRequest.mode y CreateExpenseSheetTicketRequest.mode.
  • Motivo: controla comportamiento del endpoint, no representa un enum AX de negocio.

2. Modo de borrado de líneas de hoja (deleteMode)

  • Valores: 0 LineOnly, 1 HeaderOnly, 2 WholeSheet.
  • Usos: borrado de líneas/hoja de gastos.
  • Motivo: es lógica operativa de API/controlador.

3. Modo de selección masiva de tickets (selectionMode)

  • Valores: selected, filtered.
  • Usos: vinculación masiva de tickets.
  • Motivo: es una estrategia de selección del endpoint, no enum AX.

4. Perfil interno de extracción IA (ExpenseTicketDraftProfile)

  • Valores: 0 FullDraft, 1 QuickCreate.
  • Usos: servicios internos de IA para tickets.
  • Motivo: es configuración interna de servicio, no dato de negocio AX.

Estado de implementación

  1. Tabla AX INDAxEnumAppCatalogTable creada con relación por AxEnumsTableRefRecId.
  2. Métodos mínimos de tabla y validaciones creados.
  3. getEnumValuesByName(container _data) agregado a INDCRMUtilityService.
  4. getEnumValuesById(container _data) agregado a INDCRMUtilityService.
  5. Endpoint API de lectura por nombre creado en CrmEnumsController.
  6. Endpoint API de lectura por id creado en CrmEnumsController.
  7. Pendiente: hacer que la web consuma el endpoint por nombre para pintar selects.

Recomendación final

Implementar INDAxEnumAppCatalogTable como tabla separada y enlazada directamente con INDAxEnumsTable.RecId.

La identificación de grupos de opciones sale directamente de INDAxEnumsTable.AxEnumName o INDAxEnumsTable.AxEnumId. La API debe consumir INDCRMUtilityService::getEnumValuesByName(container _data) como método principal y INDCRMUtilityService::getEnumValuesById(container _data) como alternativa separada.
